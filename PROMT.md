# PROMT: goldenroute — transparent proxy для обхода блокировок

## 1. Цель проекта

Прозрачное перенаправление трафика с устройств локальной сети и самого хоста в зависимости от геолокации целевого IP:

- **Российские IP-адреса** — трафик идёт напрямую, без прокси
- **Иностранные IP-адреса** — трафик перенаправляется в цепочку прокси-серверов
- **Tor-only IP-адреса** — трафик принудительно направляется через Tor (независимо от балансировки)
- **DNS-запросы** — перехватываются и направляются на локальный DNS-резолвер с шифрованием

Проект решает задачу обхода блокировок интернет-ресурсов на уровне сети, не требуя настройки каждого устройства. Все манипуляции с трафиком выполняются на одном хосте (шлюзе).

## 2. Архитектура системы

### 2.1. Уровни обработки трафика

Система состоит из нескольких логических уровней:

1. **Уровень перехвата трафика** — работает на уровне сетевого стека ядра. Перехватывает пакеты на разных этапах их прохождения:
   - Исходящий трафик с самого хоста (локальные процессы)
   - Входящий транзитный трафик от LAN-клиентов
   - Правила применяются на разных цепочках в зависимости от источника пакета и его типа (TCP/UDP)

2. **Уровень перенаправления (редиректа)** — принимает перехваченный трафик и распределяет его между прокси-бэкендами согласно настроенным весам балансировки. Балансировка реализована на уровне правил фильтрации (вероятностное распределение), а не на уровне приложения.

3. **Уровень прокси-бэкендов** — SOCKS5-серверы, которые принимают TCP-соединения и перенаправляют их дальше:
   - WebSocket-туннель до внешнего прокси (основной канал)
   - Tor-сеть (резервный/специализированный канал)

4. **Уровень транспорта** — обеспечивает связь между локальным прокси-сервером и внешним миром:
   - WebSocket-соединение до реверс-прокси-сервера, который передаёт трафик вышестоящему SOCKS5-прокси
   - Tor с мостами (bridges) для обхода блокировок Tor

5. **Уровень DNS** — перехватывает все DNS-запросы с LAN и хоста, форвардит их через шифрованные соединения (DNS-over-TLS) к вышестоящим DNS-серверам. Для доменов .ru используется отдельный форвард.

6. **Уровень данных о геолокации** — загружает и поддерживает в актуальном состоянии список IP-диапазонов, принадлежащих РФ (через RIPE API). Список автоматически обновляется при запуске и используется для принятия решения: проксировать или нет.

### 2.2. Схема прохождения пакета

**Запрос к российскому сайту с LAN-клиента:**
1. Пакет приходит на хост (шлюз)
2. Проверка на уровне перехвата: destination — российский IP → RETURN (не проксировать)
3. Пакет проходит через уровень форвардинга (разрешён для LAN-подсети)
4. Source-адрес заменяется на IP хоста (MASQUERADE)
5. Пакет уходит напрямую в интернет

**Запрос к иностранному сайту с LAN-клиента:**
1. Пакет приходит на хост (шлюз)
2. Проверка: destination не российский, не приватный, не адресован самому хосту
3. Проверка: не является трафиком от Docker-контейнеров (предотвращение петли)
4. Пакет перенаправляется на локальный порт прокси-балансировщика
5. Балансировщик распределяет: WebSocket-туннель (n%) или Tor (m%)
6. Прокси-сервер устанавливает соединение с внешним миром через соответствующий канал
7. Ответ возвращается клиенту через тот же путь (состояние отслеживается conntrack)

**DNS-запрос с LAN-клиента:**
1. Пакет с UDP/TCP портом 53 приходит на хост
2. Перенаправляется на локальный DNS-резолвер
3. Резолвер определяет зону: .ru → Яндекс DNS (DoT), всё остальное → Cloudflare/Google (DoT)
4. Зашифрованный ответ возвращается клиенту

## 3. Ключевые дизайн-решения и их обоснование

### 3.1. Два независимых прокси-бэкенда с балансировкой

Вместо единственного PROXY_BACKEND (выбери один) реализована балансировка между двумя бэкендами с настраиваемыми весами (в процентах). Это позволяет:
- Использовать основной канал (WebSocket-туннель) для 70% трафика
- Направлять 30% трафика через Tor для распределения нагрузки
- При отказе одного бэкенда автоматически направлять 100% трафика на работающий
- При balance=0 для обоих — отключить прокси полностью (весь трафик идёт напрямую)

Балансировка реализована на уровне правил фильтрации пакетов, а не в приложении, что исключает накладные расходы на дополнительную маршрутизацию в userspace.

### 3.2. Предотвращение петли прокси (самый важный багфикс)

Критическая проблема: трафик от Docker-контейнера nginx к вышестоящему прокси (внешний IP) попадал в цепочку PREROUTING, где destination не матчился ни под одно RETURN-правило (он не российский и не приватный) и перенаправлялся обратно в redsocks → wstunnel → nginx. Возникала петля, завершавшаяся по таймауту nginx (504 Gateway Timeout).

Решение: добавить RETURN для трафика с source-адресами из Docker bridge-сети (`172.16.0.0/12`). Все Docker-контейнеры получают IP из этого диапазона, поэтому их трафик исключается из перенаправления.

### 3.3. Использование host-сетевого режима

Сервис, управляющий правилами фильтрации, работает в режиме host-сети. Это необходимо, потому что:
- Правила применяются к сетевому стеку хоста, а не к виртуальному интерфейсу контейнера
- PROXY-сервер (redsocks) должен принимать трафик на localhost
- Без host-сети правила PREROUTING не видят трафик с хоста (только с LAN)

### 3.4. Отдельная цепочка правил вместо прямой модификации системных

Вместо того чтобы добавлять правила напрямую в системные цепочки (PREROUTING, OUTPUT), создаются пользовательские цепочки, которые подключаются одной записью. Это позволяет:
- При перезапуске контейнера удалить ТОЛЬКО свои правила (очистить свою цепочку)
- Не трогать правила, добавленные Docker или другими сервисами
- Избежать дублирования правил при множественных перезапусках

### 3.5. Блокировка QUIC с учётом геолокации

QUIC (UDP/443) — протокол, который браузеры предпочитают TCP при доступности. Прокси-серверы не поддерживают перехват UDP-трафика, поэтому QUIC-соединения к иностранным сайтам обходят прокси и уходят напрямую. Решение: блокировать QUIC для не-российских IP-адресов. Браузер, не получив ответа по UDP, автоматически откатывается на TCP/443, который перехватывается прокси.

Особенности реализации:
- QUIC **разрешён** для российских IP-адресов (российские сайты должны работать напрямую и быстро)
- QUIC **заблокирован** для иностранных IP-адресов
- Блокировка применяется в FORWARD (транзитный трафик LAN) и OUTPUT (трафик с хоста)
- Для OUTPUT есть исключение для source-адреса 127.0.0.1 (внутренние процессы)
- Правила применяются только когда прокси включён

## 4. Структура кода

```
fw/                          — Управление трафиком (центральный компонент)
  ├── Dockerfile              — Сборка образа
  ├── entrypoint.sh           — Главный скрипт (точка входа контейнера)
  ├── russian-ips.txt         — Кеш диапазонов российских IP (обновляется с RIPE)
  └── tor-only-ips.txt        — Список IP/подсетей, форсирующих Tor

nginx/                       — Реверс-прокси для WebSocket-туннеля
  ├── entrypoint.sh           — Скрипт генерации конфигурации nginx
  └── backends.list           — Список вышестоящих прокси-серверов

unbound/                     — DNS-резолвер с DoT
  ├── Dockerfile
  ├── entrypoint.sh
  └── unbound.conf            — Конфигурация DNS-форвардинга

tor/                         — Tor-клиент с мостами
  ├── Dockerfile
  ├── docker-entrypoint.sh
  ├── torrc                   — Конфигурация Tor
  └── bridges.txt             — Список мостов Tor

docker-compose.yml           — Оркестрация сервисов
.env                         — Переменные окружения (балансировка, порты)
```

### 4.1. Логика fw/entrypoint.sh (главный скрипт)

Скрипт выполняется при старте контейнера и выполняет последовательно:

1. **Валидация параметров** — проверяет, что балансы неотрицательные целые числа, их сумма равна 100 (если прокси включён)
2. **Очистка старых правил** — удаляет пользовательские цепочки из nat-таблицы
3. **Загрузка tor-only IP** — загружает список адресов, которые всегда должны идти через Tor
4. **Загрузка российских IP** — загружает из файла (с RIPE при старте), создаёт пустой set, если прокси выключен
5. **Запуск redsocks** — запускает SOCKS5-прокси для каждого активного бэкенда (wstunnel на порту 12345, Tor на порту 12346)
6. **Настройка правил OUTPUT** — для трафика с хоста
7. **Настройка правил PREROUTING** — для трафика с LAN
8. **Настройка балансировки** — вероятностное распределение между бэкендами
9. **Healthcheck-цикл** — проверяет доступность бэкендов, переконфигурирует балансировку при отказе одного из них
10. **Правила QUIC** — блокировка UDP/443 для не-российских IP (только при включённом прокси)
11. **Поддержание контейнера** — бесконечный цикл с sleep

Скрипт корректно обрабатывает сигналы завершения через trap, убивая запущенные процессы при остановке контейнера.

## 5. Переменные конфигурации

Система управляется через переменные окружения в `.env`:

| Параметр | Назначение | Особенности |
|----------|-----------|-------------|
| `TOR_BALANCE` | Процент трафика через Tor (0-100) | 0 = Tor отключён |
| `WSTUNNEL_BALANCE` | Процент трафика через wstunnel (0-100) | 0 = wstunnel отключён |
| `LL_IPV4_ADDR` | IP привязки сервисов | `127.0.0.1` для локального доступа, `0.0.0.0` для доступа с LAN |
| `LLP_SOCKS5_PROXY` | Порт SOCKS5-прокси для ручного использования | |
| `LLP_HTTP_PROXY` | Порт HTTP-прокси для ручного использования | |
| `UNBOUND_PORT` | Порт DNS-сервера | Должен быть 53 для перехвата |
| `TOR_SOCKS_PORT` | Порт Tor SOCKS5 | Используется как апстрим для redsocks |

**Важно:** Если `LL_IPV4_ADDR=0.0.0.0`, необходимо указать `PAC_PROXY_HOST` (переменная для PAC-файла), иначе клиенты не смогут подключиться к прокси по правильному адресу.

Балансировка: при `TOR_BALANCE=30` и `WSTUNNEL_BALANCE=70` — 30% трафика идёт через Tor, 70% через WebSocket-туннель. Сумма должна быть 100. Если оба = 0, прокси отключён.

## 6. Принципы разработки

### 6.1. Принцип идемпотентности

Все операции (создание цепочек, добавление правил) должны быть идемпотентными. Перед добавлением правила выполняется очистка старого через while-цикл удаления (удалять, пока удаляется). Это позволяет:
- Перезапускать контейнер без ошибок дублирования правил
- Многократно применять один и тот же скрипт
- Гарантировать, что после выполнения скрипта правила ровно один раз

### 6.2. Graceful degradation

Система должна сохранять работоспособность при частичных отказах:
- При недоступности RIPE — используется кешированный файл российских IP
- При недоступности одного бэкенда — трафик перенаправляется на другой (через healthcheck)
- При отказе обоих бэкендов — трафик идёт напрямую (правила PREROUTING продолжают работать, но redirection не происходит)
- При пустом списке российских IP — весь трафик считается иностранным и проксируется

### 6.3. Минимизация состояния

Скрипт не использует файлы состояния. Вся конфигурация определяется:
- Переменными окружения (на момент запуска)
- Файлами данных (russian-ips.txt, tor-only-ips.txt, backends.list)
- Текущим состоянием сетевого стека (проверка live-статуса бэкендов)

### 6.4. Конвенции кода

- Все сообщения в stdout/stderr имеют префикс `[fw]`, `[nginx]`, `[tor]`, `[unbound]` для идентификации источника в логах Docker
- Критичные ошибки завершают скрипт с exit 1 (видны в docker compose logs)
- Некритичные ошибки логируются, но не прерывают выполнение (через `|| true` или проверки)
- Использовать sh (не bash) для максимальной совместимости с минимальными образами (Alpine)
- Комментарии в скриптах — на русском языке для основной команды

## 7. Типовые сценарии

### 7.1. Добавление нового бэкенда

1. Определить порт для SOCKS5-апстрима (например, 12347)
2. Добавить запуск redsocks для нового порта в `entrypoint.sh`
3. Добавить порт в список RETURN-исключений (чтобы не перехватывать свой же трафик)
4. Расширить configure_lb для поддержки трёх бэкендов
5. Обновить healthcheck

### 7.2. Изменение LAN-подсети

Заменить `192.168.1.0/24` на нужную подсеть во всех правилах:
- DOCKER-USER (FORWARD)
- MASQUERADE (POSTROUTING)

### 7.3. Добавление tor-only адресов

Добавить IP-адреса или CIDR-диапазоны в `fw/tor-only-ips.txt` (по одному на строку, решётки для комментариев). Трафик к этим адресам будет перенаправляться на порт Tor-redsocks, минуя общую балансировку.

## 8. Важные нюансы и подводные камни

### 8.1. Петля прокси (см. раздел 3.2)

Самая частая проблема при модификации правил — создание петли, когда трафик от Docker-контейнера к внешнему прокси снова перехватывается и направляется в прокси. Защита: RETURN для source `172.16.0.0/12`.

### 8.2. QUIC и откат на TCP

Блокировка QUIC должна применяться ТОЛЬКО при включённом прокси. Если прокси отключён, блокировка QUIC приведёт к деградации соединений с иностранными сайтами (браузер будет долго ждать таймаута UDP, прежде чем переключиться на TCP).

### 8.3. Порядок правил имеет значение

Правила RETURN должны предшествовать правилам REDIRECT/DROP. Если поставить REDIRECT раньше RETURN, все пакеты будут перенаправлены независимо от геолокации. Особенно важно для правил:
- `dst-type LOCAL` должно быть ПЕРВЫМ в PREROUTING (иначе пакеты к самому хосту будут перехвачены)
- source `172.16.0.0/12` должно быть ПЕРВЫМ после LOCAL (предотвращение петли)
- `russian-ips dst` должно быть ПЕРЕД правилом перенаправления

### 8.4. Docker-USER vs FORWARD

Docker использует цепочку `DOCKER-USER` для пользовательских правил форвардинга. Правила, добавленные напрямую в FORWARD, могут быть удалены Docker при перезапуске. Все правила FORWARD должны добавляться в DOCKER-USER.

### 8.5. RIPE-обновление в фоне

Обновление списка российских IP с RIPE выполняется в фоновом процессе (`&`), чтобы не задерживать запуск контейнера. Если RIPE недоступен, используется кеш из файла. Пока кеш пуст (первый запуск), весь трафик будет проксироваться — это приемлемо, так как после загрузки списка правила применяются атомарно через ipset swap.

### 8.6. Conntrack и MASQUERADE

MASQUERADE полагается на conntrack для обратного пути пакетов. Если conntrack таблица переполнена или сброшена, существующие соединения могут прерваться. При перезапуске fw-контейнера старые соединения LAN-клиентов могут временно потерять связь до переустановки соединения.

## 9. Тестирование и отладка

### 9.1. Проверка правил фильтрации

После применения правил проверить:
- Правила присутствуют в нужных цепочках (PREROUTING, OUTPUT, FORWARD/DOCKER-USER)
- Российские IP не перенаправляются (счётчик правил не растёт)
- Иностранные IP перенаправляются (счётчик REDIRECT растёт)
- Балансировка распределяет трафик согласно настроенным весам

### 9.2. Проверка QUIC

- QUIC к российскому IP (например, Яндекс) — не блокируется
- QUIC к иностранному IP (например, Google 8.8.8.8) — блокируется (счётчик DROP растёт)

### 9.3. Проверка прокси-цепочек

При отказе одного бэкенда (wstunnel или Tor) трафик автоматически перенаправляется на работающий. Проверка: остановить один сервис, убедиться, что healthcheck переключил балансировку, и весь TCP-трафик идёт через работающий бэкенд.

### 9.4. Типовые команды отладки

- Просмотр логов всех сервисов
- Проверка правил фильтрации
- Проверка статистики ipset
- Проверка доступности бэкендов изнутри контейнера
- Проверка счётчиков пакетов в правилах

## 10. Потенциальные улучшения

- Поддержка IPv6 (сейчас только IPv4)
- Поддержка UDP-прокси для QUIC (не все прокси-решения поддерживают)
- Мониторинг и алертинг при падении бэкендов
- Автоматическое переключение при превышении порога ошибок (сейчас — только бинарная проверка доступности порта)
- Graceful degradation при переполнении conntrack
- Hot-reload конфигурации без перезапуска контейнера
- Поддержка произвольного количества бэкендов (сейчас — ровно два)
