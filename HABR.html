РЕШЕНИЕ: GOLDENROUTE™

GOLDENROUTE™ — это 3 (три) Docker-контейнера, которые превращают любой Linux-хост в прозрачный шлюз для обхода блокировок.

Что он делает:

  1. Перехватывает весь TCP-трафик с LAN и хоста
  2. Проверяет destination: российский? → пропускает напрямую. В списке исключений? → пропускает напрямую. Всё остальное? → в Tor.
  3. Перехватывает все DNS-запросы и направляет их через DoT (DNS-over-TLS)

Что он НЕ делает:

  • Не анонимизирует (Tor здесь — средство обхода блокировок, не более)
  • Не требует настройки на каждом устройстве
  • Не требует VPN-клиентов
  • Не требует покупки VPS

КАК ЭТО РАБОТАЕТ (БЕЗ АСКЕТИЧНЫХ ASCII-СХЕМ)

Система принимает 3 (три) решения о каждом пакете:

  1. Destination в russian-ips → RETURN. Трафик идёт напрямую. Российские адреса не требуют посредников. Список диапазонов загружается с RIPE API и автоматически обновляется.
  2. Destination в tor-exclude → RETURN. Ваш персональный список исключений. Вы сами решаете, что не должно касаться Tor.
  3. Всё остальное → REDIRECT → Tor. Без обсуждений.

Цепочки iptables

Их 3 (три). И каждая делает ровно то, для чего предназначена.

1. FW_REDIRECT (PREROUTING)

Встречает трафик от LAN-клиентов. Порядок проверки критичен — нарушение фатально:

dst-type LOCAL        → RETURN   # пакеты самому хосту
src 172.16.0.0/12     → RETURN   # Docker bridge (анти-петля)
10/8, 172.16/12,      → RETURN   # приватные диапазоны
192.168/16
russian-ips           → RETURN   # домашняя территория
tor-exclude           → RETURN   # ваши исключения
dport 12346/9050      → RETURN   # не перехватывать свой трафик
dport 53              → REDIRECT # DNS → unbound
всё остальное TCP     → REDIRECT # → :12346 → Tor

2. FW_OUTPUT (OUTPUT)

Абсолютно та же логика для трафика, рождённого на хосте. Хост не является исключением.

3. DOCKER-USER (FORWARD)

Разрешает транзитный трафик из LAN и MASQUERADE для SNAT.

QUIC — ПРОТОКОЛ, КОТОРЫЙ ДУМАЕТ, ЧТО ОН ВЫШЕ TCP

QUIC (UDP/443) — протокол, который браузеры предпочитают TCP при любой возможности.

Прокси-серверы не поддерживают перехват UDP. Если QUIC не заблокировать, браузер устанавливает прямое соединение с иностранным сервером, минуя Tor. Весь смысл системы теряется.

Решение — блокировка QUIC для всего, что не в russian-ips и не в tor-exclude:

FORWARD: UDP/443 !russian-ips !tor-exclude → DROP
OUTPUT:  UDP/443 !127.0.0.1 !russian-ips !tor-exclude → DROP

Браузер, не получив ответа по UDP, откатывается на TCP/443. TCP/443 перехватывается правилами PREROUTING/OUTPUT и направляется в Tor.

QUIC к российским сайтам и к адресам из вашего списка исключений работает штатно — без задержек, без потери производительности.

КОМПОНЕНТЫ

fw (Firewall)

Центральный компонент. network_mode: host, права NET_ADMIN + NET_RAW. Управляет iptables на хосте напрямую.

При старте:

  1. Очищает старые цепочки через while-цикл (идемпотентность — обязательное требование)
  2. Загружает ipset russian-ips из файла + фоновое обновление с RIPE (4 попытки)
  3. Загружает ipset tor-exclude из файла
  4. Запускает redsocks на порту 12346, апстрим — Tor SOCKS5 :9050
  5. Применяет правила к OUTPUT и PREROUTING
  6. Блокирует QUIC для не-российских и не-исключённых адресов

При остановке: trap cleanup убивает redsocks и убирает за собой.

tor

Единственный бэкенд. SOCKS5 на порту 9050. Мосты obfs4 для обхода блокировок. Никакой балансировки, никаких альтернатив.

unbound

DNS-over-TLS форвардер. Все DNS-запросы с LAN и хоста перехватываются на порту 53 и направляются сюда. .ru — через Яндекс DNS (DoT), всё остальное — через Cloudflare и Google (DoT).

ОДИН ДЕНЬ ИЗ ЖИЗНИ ПОЛЬЗОВАТЕЛЯ GOLDENROUTE™

Утро. Вы открываете ноутбук. Он подключается к Wi-Fi. Вы получаете IP по DHCP. Шлюз по умолчанию — хост с GOLDENROUTE™. DNS — хост с GOLDENROUTE™. Вы открываете Яндекс — он открывается напрямую, без Tor. Быстро.

День. Вы открываете заблокированный сайт. Браузер сначала пробует QUIC (UDP/443) — пакет тихо дропается. Браузер откатывается на TCP/443. Пакет попадает в PREROUTING, destination не российский, не в исключениях. REDIRECT :12346. redsocks → Tor. Сайт открывается.

Вечер. Ребёнок открывает YouTube на планшете. Никаких настроек. Никаких вопросов. Просто работает.

ДИАГНОСТИКА

Tor не забутстрапился:

docker compose logs tor | grep "Bootstrapped"

Ожидается Bootstrapped 100% (done). Если нет — обновить мосты на https://bridges.torproject.org.

Трафик не идёт через Tor:

docker compose exec fw iptables -t nat -L FW_REDIRECT -n -v

Счётчик REDIRECT tcp --dport 12346 должен расти.

QUIC не блокируется:

docker compose exec fw iptables -L FORWARD -n -v | grep "udp dpt:443"

Счётчик DROP должен расти на иностранных сайтах.

Мосты заблокированы:

docker compose up -d --force-recreate tor

ОГРАНИЧЕНИЯ (ЧЕСТНОСТЬ — ЛУЧШАЯ ПОЛИТИКА)

  • Только TCP уходит через Tor. UDP (кроме DNS и заблокированного QUIC) — напрямую.
  • Snowflake не работает через Docker NAT. Только obfs4-мосты.
  • network_mode: host обязателен для fw.
  • Только IPv4.

ПОЧЕМУ НЕ WSTUNNEL? ПОЧЕМУ НЕ БАЛАНСИРОВКА?

В предыдущей версии проекта было 2 (два) бэкенда: wstunnel (WebSocket-туннель до вышестоящего SOCKS5-прокси) и Tor. Между ними — вероятностная балансировка 70/30.

Практика показала: балансировка между платным прокси и Tor — это компромисс, который не нужен никому. Tor справляется с обходом блокировок. Если вам нужна производительность — используйте Tor с правильными мостами. Если вам нужна анонимность — используйте Tor. Два бэкенда — это не гибкость. Это лишняя сложность.

GOLDENROUTE™ — это один бэкенд. Одно направление. Tor.
