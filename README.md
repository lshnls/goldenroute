# goldenroute — transparent proxy для обхода блокировок

## Назначение

Маршрутизация трафика с LAN и локального хоста в зависимости от адреса назначения:
- **Российские IP** (список RIPE) → напрямую
- **Ваши персональные исключения** (`fw/tor-exclude-ips.txt`) → напрямую
- **Весь остальной (иностранный) трафик** → Tor
- **DNS** → шифрованные DoT-запросы через unbound; для `.ru` — через Яндекс DNS

Только обход блокировок, без анонимности. Единственный бэкенд — Tor: сезон балансировки между несколькими прокси закрыт, wstunnel и nginx из коллекции сняты.

## Архитектура

```
┌──────────────┐    DNS :53    ┌──────────┐    DoT (853)
│   Клиенты    │ ────────────→ │  unbound  │ ─────────→ Cloudflare/Google/Yandex
│ 192.168.1.0/24│              └──────────┘
└──────┬───────┘
       │ шлюз по умолчанию: <IP хоста>
       ▼
┌─────────────────────────────────────────────────────────────────┐
│                          хост (network_mode: host)               │
│                                                                   │
│  ┌──────────────────┐    TCP     ┌──────────────────┐            │
│  │  iptables (fw)   │ ─────────→ │    redsocks-tor   │            │
│  │  OUTPUT/PREROUTING│            │  :12346 → socks5  │            │
│  │  + FORWARD        │            │  127.0.0.1:9050   │            │
│  │  + MASQUERADE     │            └────────┬─────────┘            │
│  └──────────────────┘                      │                      │
└─────────────────────────────────────────────┼──────────────────────┘
                                               ▼
                                        ┌──────────────┐
                                        │     tor      │
                                        │  мосты obfs4 │
                                        └──────┬───────┘
                                               ▼
                                            ИНТЕРНЕТ
```

Логика маршрутизации IP (цепочка iptables nat `FW_REDIRECT`/`FW_OUTPUT`):
1. dst-type LOCAL → RETURN
2. source из Docker bridge (`172.16.0.0/12`) → RETURN (предотвращает петли)
3. dst в приватные диапазоны → RETURN
4. dst в ipset `russian-ips` (данные RIPE) → RETURN
5. dst в ipset `tor-exclude` (ваш список, `fw/tor-exclude-ips.txt`) → RETURN
6. dst порт `12346` или `9050` (сам redsocks-tor / Tor) → RETURN
7. dst порт 53 (UDP/TCP) → REDIRECT на `:53` (unbound)
8. весь остальной TCP → REDIRECT на `:12346` (redsocks-tor → Tor)

QUIC (UDP/443) для всего, что не в `russian-ips` и не в `tor-exclude`, дропается — браузер откатывается на TCP:443 и попадает в тот же путь через Tor.

## Сервисы

| Сервис | Образ | Роль |
|--------|-------|------|
| `fw` | кастомный (alpine + iptables + redsocks) | правила iptables, прозрачное перенаправление в Tor, определение российских IP |
| `tor` | кастомный (alpine + tor + lyrebird) | единственный бэкенд для иностранного трафика, мосты obfs4 |
| `unbound` | кастомный (alpine + unbound) | DNS-over-TLS форвардер |

## Устройство fw

1. **Загрузка ipset `russian-ips`** — из `fw/russian-ips.txt`, дальше обновляется в фоне из RIPE каждый запуск.
2. **Загрузка ipset `tor-exclude`** — из `fw/tor-exclude-ips.txt`, статический список, обновляется только вручную.
3. **Запуск redsocks-tor** — стартует в фоне на порту `12346`. Принимает переадресованный iptables трафик и перенаправляет его в SOCKS5 Tor на порту `9050`.
4. **Применение правил** к цепочкам `OUTPUT` (трафик хоста) и `PREROUTING` (трафик LAN-клиентов) — идентичная логика для обоих.

Область действия `OUTPUT`: только процессы на хосте. Docker-контейнеры (tor, unbound) не попадают в эту цепочку — у них собственная маршрутизация через bridge-сеть Docker.

### Зачем RETURN на `172.16.0.0/12`

Все Docker bridge-сети используют этот диапазон. Без этого правила трафик между контейнерами попадал бы в перенаправление вместо прямого пути.

### Путь пакета целиком

```
LAN-клиент → PREROUTING (FW_REDIRECT) → REDIRECT :12346 → redsocks-tor
→ socks5 127.0.0.1:9050 → Tor (мосты obfs4) → ИНТЕРНЕТ
```

## Файлы данных

### `fw/russian-ips.txt`

Список российских диапазонов (данные RIPE). Обновляется автоматически при каждом запуске контейнера `fw` — не редактируйте вручную, изменения будут перезаписаны.

### `fw/tor-exclude-ips.txt`

Ваш персональный список — адреса, которые **не должны** идти через Tor, в дополнение к `russian-ips.txt`. Формат: один IP или CIDR на строку, `#` — комментарий.

```
# Пример:
104.18.0.0/16
1.2.3.4
```

Полезно для сервисов, которые блокируют или замедляют запросы через Tor-exit-ноды, либо для доменов, которым принципиально не нужна анонимизация через Tor.

## Быстрый старт

```bash
# 1. Клонировать и подготовить
git clone <repo> goldenroute
cd goldenroute
cp .env.example .env

# 2. Получить свежие мосты Tor на https://bridges.torproject.org
#    и вписать их в tor/bridges.txt (формат: строки "Bridge obfs4 ...")

# 3. При необходимости — добавить адреса в fw/tor-exclude-ips.txt

# 4. Запустить
docker compose up -d
```

### Настройка клиентов (LAN)

На каждом клиенте в LAN укажите:
- Шлюз по умолчанию: IP хоста, на котором запущен `goldenroute`
- DNS: IP хоста (unbound слушает `$UNBOUND_PORT`, по умолчанию 53)

## Переменные окружения (`.env`)

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `UNBOUND_PORT` | `53` | Порт DNS |
| `TOR_SOCKS_PORT` | `9050` | Порт SOCKS5 Tor (публикуется наружу для `fw`) |
| `TOR_CONTROL_PORT` | `9051` | Control-порт Tor |
| `TOR_REDSOCKS_PORT` | `12346` | Порт, на котором внутри `fw` слушает redsocks-tor |
| `LAN_CIDR` | `192.168.1.0/24` | Подсеть LAN, для которой применяются правила ACCEPT/MASQUERADE |

## Диагностика

### Трафик не идёт через Tor

1. Проверьте, что Tor забутстрапился: `docker compose logs tor` — ищите `Bootstrapped 100% (done)`.
2. Проверьте, что запущен `redsocks-tor` и слушает порт: `docker compose exec fw ss -tlnp`.
3. Проверьте счётчики правил: `docker compose exec fw iptables -t nat -L FW_REDIRECT -n -v` — растут ли пакеты на правиле `REDIRECT :12346`.

### Мосты не бутстрапятся

Мосты имеют свойство блокироваться со временем. Получите свежий набор на https://bridges.torproject.org и пересоздайте контейнер:

```bash
docker compose up -d --force-recreate tor
```

### DNS не резолвится

Проверьте, что unbound запущен и клиент действительно использует его как DNS-сервер (`nslookup example.com <IP-хоста>`).

## Известные ограничения

- Только TCP уходит в Tor через redsocks (SOCKS5 не поддерживает UDP) — UDP, кроме DNS и заблокированного QUIC, идёт напрямую.
- Snowflake не работает через Docker (WebRTC/UDP не проходит через Docker NAT). Используйте obfs4-мосты.
- `network_mode: host` обязателен для `fw` — в любом другом режиме правила iptables не будут применяться к трафику хоста и LAN.
